# 0004 - Module boundaries via per-module Contracts projects

**Status:** Accepted

## Context

In a modular monolith, the module boundary is only as real as what the compiler enforces. If any module can add a project reference straight to another module's main project, it can reach its entities, its `DbContext`, its internal handlers - and the "modular" part of modular monolith erodes one convenient shortcut at a time, usually without anyone deciding that should happen.

At the same time, modules genuinely need to talk to each other: Bookings needs to know a unit's price and confirm/release a hold (Catalog); Transactions needs to look up and confirm a booking (Bookings); Bookings needs to resolve/reverse a transaction (Transactions); Identity needs to register a host (Hosts).

A related question: what belongs in the shared kernel (`SeedWork`, `BuildingBlocks`) versus a single module? Early on, several types lived in the shared kernel by default (e.g. `BookingNotPayableException`, `PropertyType`) without a second module actually needing them - "might be shared later" isn't the same as "is shared."

## Decision

**Cross-module access goes through a `<Module>.Contracts` project, never the module's main project.**

- Each module that's referenced by another module exposes a sibling `<Module>.Contracts` project, physically nested inside the owning module's folder but built as a separate assembly (`Catalog.Contracts`, `Bookings.Contracts`, `Hosts.Contracts`, `Transactions.Contracts`).
- `Contracts` projects hold only what's needed for cross-module calls: interfaces (`IUnitLookup`, `IHoldConfirmation`, `IBookingLookup`, `IBookingPaymentConfirmation`, `ITransactionReversal`, `IHostRegistrar`, `IHostAuthorization`, `IHostLookup`) and their DTOs.
- The interface's implementation is an `internal` class living in the *main* module project (`Catalog.Contracts.UnitLookup` implemented by `internal class UnitLookup` in `Catalog`), registered against the interface in that module's own `ServicesRegistration`. Other modules can only ever resolve it through DI against the interface - the concrete type isn't visible outside its own assembly.
- A domain exception that's actually thrown from more than one module's code (not just carried in a shared DTO) lives in the *owning* module's `Contracts` project, not the shared kernel - `BookingNotPayableException` lives in `Bookings.Contracts` because Bookings' own `Booking.Confirm()` and Transactions' `InitiateTransactionHandler` both throw/rely on it, deferring to Bookings' own invariant.
- `SeedWork`/`BuildingBlocks` hold only what's genuinely used by name from two or more modules already - `Entity`, `Currency`, `EntityStatus`, the soft-delete convention, pagination helpers. The test is "does another module actually reference this by name today," not "this looks generic." Types that failed that test (found during an audit) were moved out into the one module that actually used them.

A module's own main `.csproj` explicitly excludes its nested `Contracts` folder from its own compilation (`<Compile Remove="X.Contracts\**"/>`) - without this, SDK-style default globbing compiles the nested project's files into both assemblies (`CS0436` ambiguous-type errors), since the folder is physically inside the parent but is its own project.

## Alternatives considered

- **Modules reference each other's main project directly**, relying on code review discipline to avoid reaching into internals. Rejected: discipline erodes under deadline pressure in a way a missing project reference cannot - the compiler is a much cheaper enforcement mechanism than a reviewer catching every violation.
- **One shared "Contracts" project for the whole solution**, rather than one per module. Rejected: it would still compile-time-couple every module to every other module's contracts even when no relationship exists, and would immediately become the new dumping ground the shared-kernel test above was meant to prevent.
- **A generic shared kernel by default**, moving things out only if they turn out to need to be module-specific. This is what happened before this decision was made explicit, and it's why the audit above was needed - the default direction matters, and "shared until proven otherwise" reliably accumulates more than "local until proven shared."

## Consequences

- A new cross-module capability costs a small amount of ceremony (an interface in `Contracts`, an `internal` implementation, a DI registration) that a direct reference wouldn't. This is the deliberate cost of the boundary being real.
- Adding a *new* module-to-module relationship for the first time also means creating that module's `Contracts` project if it doesn't already have one, including the `Compile Remove` guard in its own `.csproj`.
- Whether a new shared-looking type belongs in `SeedWork`/`BuildingBlocks` or a specific module's `Contracts` project should keep being decided by the same test: is something *else*, right now, actually referencing it by name - not whether it looks reusable.
- **Worked example of the boundary running in the direction it's usually described against.** `Bookings.Jobs.ReconcileOrphanedBookedHoldsJob` (see [ADR-0003](0003-compensating-actions-over-distributed-transactions.md)'s Consequences) needs to know which Catalog holds look orphaned - the obvious shortcut would be a raw SQL query joining `unit_availability_holds` by table name directly, since the job already runs raw SQL elsewhere in this codebase's Tier 3 style. That's exactly the boundary violation this ADR exists to prevent: the compiler can't see a table name inside a SQL string, no matter which module's assembly the query happens to run from. The actual fix cost one interface: `Catalog.Contracts.IHoldLookup.GetBookedHoldIdsOlderThanAsync`, implemented by `internal class HoldLookup` in Catalog, returning candidate hold ids to Bookings, which then checks those ids against its own `bookings` table and calls the existing `IHoldConfirmation.ReleaseHoldAsync` for the orphans. Two round trips instead of one join, boundary intact.
- **A per-module `Contracts` project stops a module reaching another's internals, but says nothing about direction - the graph can still grow a cycle.** This happened for real: `DeleteUnitHandler`/`DeletePropertyHandler` needed one fact only Bookings has (does this unit have a live booking) to refuse archiving out from under a guest, and the fix that shipped was `Catalog` adding a project reference to `Bookings.Contracts.IBookingLookup`. Since `Bookings` already referenced `Catalog.Contracts` (for `IUnitLookup`/`IHoldConfirmation`), that made `Catalog` and `Bookings` mutually dependent - two of six modules that could no longer be reasoned about, tested, or (hypothetically) extracted independently of each other, which is the entire payoff a modular monolith is for. Nothing in this ADR's checklist would have caught it: the new reference was Contracts-only, `internal` was still respected, DI was used correctly - every rule here was followed and the graph still went cyclic.
- **The direction rule this ADR was missing:** order the modules by how far downstream of raw inventory they sit - `Hosts → Catalog → Availability → Promotions → Bookings → Transactions` (`Reviews` sits off to the side, consuming any of the others but providing no `Contracts` of its own). A module may depend on an earlier module's `Contracts`, never a later one's. When the fact you need lives in a *later* module - as "does this unit have a booking" lives in Bookings, one step downstream of Catalog - the interface still has to be *declared* on the earlier module's side (here, `Catalog.Contracts.IUnitArchivalGuard`) and *implemented* on the later one's side, registered against that interface in the later module's own `ServicesRegistration` (`Bookings.Contracts.UnitArchivalGuard`, registered in `BookingsServicesRegistration`). The later module can implement the earlier module's interface for free, since it already legitimately depends on that module's `Contracts` project - only the earlier module is ever forbidden from reaching forward. This is the same dependency-inversion move as everywhere else in this codebase (depend on an abstraction, not the module that happens to answer it), just applied for the first time to a case where the *asker* is upstream of the *answerer*.
- **`Bookings` and `Transactions` were already mutually dependent before this pass, by original design** (see this ADR's own Context: "Transactions needs to look up and confirm a booking (Bookings); Bookings needs to resolve/reverse a transaction (Transactions)"). The direction rule above says this pair should be acyclic too (`Transactions` is downstream of `Bookings`, so `Bookings` should never reach into `Transactions.Contracts`) - `CancelBookingHandler`'s use of `ITransactionReversal` is the edge that violates it. Left as-is for now since it predates this pass and un-picking it is a larger, separate change; flagged here so it isn't mistaken for having been reviewed and accepted under this rule.
- **New module relationships should be checked against this rule going forward**, the same way `Compile Remove` and `internal` are already checked - before adding a `ProjectReference` to another module's `Contracts` project, confirm that module isn't already downstream in this order. A quick way to check: does the *target* module (or its `Contracts` project) already reference the module you're editing, directly or transitively? If yes, don't add the direct reference - define the interface on your own side instead, per the pattern above.
- **`Promotions` was extracted from `Catalog` after a size/cohesion review** (4,467 LOC across four unrelated concerns - listings, pricing, holds, promotions - versus every other module's few hundred to ~1,600) rather than a boundary violation this time. `Promotion`/`PromotionRedemption` were the clean case: `IPromotionRedemption`'s only consumer was ever Bookings, exactly the ADR-0004 "does another module reference this by name today" test passing on its own. Slotted in at `Catalog → Promotions → Bookings` in the direction order above - `Promotions` depends on `Catalog.Contracts.IUnitLookup` (already-existing, already carrying `HostId` on `UnitSummary` for Reviews' own unrelated need) to check a redeemed code's host-scoping, replacing what used to be two local EF reads against `Unit`/`Property` inside the same `AppCatalogDbContext`. `UnitAvailabilityHold` was the other candidate the same review raised, initially left in `Catalog` given its hot paths' tighter coupling to `Unit` - see the next entry for why it was extracted after all, and how that coupling was actually resolved.
- **`Availability` was extracted from `Catalog` next, on explicit direction to pursue the ideal split despite the coupling cost flagged above.** `UnitAvailabilityHold` - the highest-concurrency table in the app, governed by its own absolute Tier-3 rule (docs/adr/0014) and GIST exclusion constraint (docs/adr/0010) - shared a module with low-frequency Property/Unit CRUD for no reason other than history. Slotted in at `Catalog → Availability → Promotions` in the direction order above. Three real coupling points had to be resolved, all via the same "declare on the asker's side" pattern already established for `IUnitArchivalGuard`:
  - `HoldAvailabilityHandler` needed a unit's price/capacity to compute a hold's snapshot - resolved via a new `Catalog.Contracts.IUnitLookup.ResolveStayPricingAsync(unitId, checkIn, checkOut, ct)`, which runs `PricingCalculator` (unmoved, still Catalog-internal) against Catalog's own `Unit`/`PricingRule` tables and returns the resolved total plus `MaxOccupancy` in one call - replacing two local EF reads this handler used to do directly, back when it lived in the same module as both tables.
  - `GetPriceCalendarHandler`'s single Tier-3 SQL statement joining `units` and `unit_availability_holds` directly by table name became exactly the boundary violation this ADR exists to prevent, once the second table moved to a different module's schema ownership. Replaced by a new `Catalog.Contracts.IUnitAvailabilityLookup.GetActiveHoldRangesAsync`, implemented by Availability, returning the unit's active hold ranges for the requested window; the per-day containment check that used to be a SQL `NOT EXISTS` subquery is now a trivial C# `.Any()` over at most a handful of ranges.
  - `GetPropertiesHandler`'s composed, lazily-executed subquery (`matchingUnits.Where(u => !dbContext.UnitAvailabilityHolds.Any(...))`) had the same problem in bulk form - fixed via the same interface's `GetUnitIdsWithOverlappingHoldAsync(unitIds, checkIn, checkOut, now, ct)`, which means the capacity-filtered candidate unit ids now have to be materialized before the availability check runs, rather than composed into one lazy query executed at the end. One extra round trip on a cache-fronted (30s `HybridCache`), non-latency-critical search endpoint - an accepted, deliberate cost, not an oversight. That materialized `List<Guid>` is also unbounded, unlike `ReconcileOrphanedBookedHoldsJob`'s own candidate query (capped at `MaxResultsPerRun`) - fine at this app's current unit count, but a Guests-only search with no city/property-type filter would materialize every capacity-matching unit and send/`IN`-clause an equally large id array on both sides of the round trip. Not urgent today; worth capping if this app's unit count reaches the tens of thousands.
  - `DeleteUnitHandler`/`DeletePropertyHandler`'s inline "does this unit have any hold" check became the same interface's `HasActiveHoldForUnitAsync`, preserving its exact existing semantics (no expiry filter - an un-swept expired `'held'` row still blocks archival) rather than "fixing" it as a drive-by change.

  `IHoldConfirmation`/`IHoldLookup` (Bookings' existing write/read contracts against holds) moved wholesale to `Availability.Contracts` with no interface changes - `Bookings.Jobs.ReconcileOrphanedBookedHoldsJob` and `ConfirmBookingHandler`/`CancelBookingHandler` needed only a `using` change, since the contracts themselves didn't need to change shape, only which module's assembly they live in. Both migrations for this move (Catalog dropping the entity from its tracked model, Availability adding it to its own) are empty-bodied, same pattern as the `Promotions` extraction above - the table, its indexes, and its exclusion constraint never physically moved, since every module already shares one Postgres schema.
