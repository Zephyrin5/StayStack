# 0003 - Compensating actions and a transactional outbox for cross-module writes

**Status:** Accepted; partially superseded by [ADR-0017](0017-durable-intent-records-for-cross-module-writes.md)

> ADR-0017 replaces this document's treatment of the *forward* half of
> `ConfirmBookingHandler` - the reconciliation jobs described in Consequences
> below are superseded by a durable intent record and a single job driven by
> it. The mechanism this ADR establishes (the outbox itself, its dispatch and
> dead-letter model, and the compensating-action shape) is unchanged and still
> governs `CancelBookingHandler` and `MarkTransactionSucceededHandler`, both of
> which already write their outbox row in the same `SaveChangesAsync` as the
> state change and are not affected.

## Context

This is a modular monolith: each module (Identity, Catalog, Hosts, Bookings, Transactions) owns its own `DbContext` and, conceptually, its own database boundary, even though they currently share one physical Postgres instance. Several real workflows need to write across two modules as one logical operation:

- **Becoming a host** (`BecomeHostHandler`): registers a `Host` (Hosts module) and links it to the caller's `ApplicationUser` (Identity module).
- **Confirming a booking** (`ConfirmBookingHandler`): marks a hold `booked` (Availability) and inserts the `Booking` row (Bookings).
- **A payment resolving** (`MarkTransactionSucceededHandler`): marks a `Transaction` succeeded (Transactions) and confirms the `Booking` (Bookings) - or, if the booking was already cancelled by the time payment resolved, starts a refund instead.
- **Cancelling a booking** (`CancelBookingHandler`): cancels the `Booking` (Bookings), releases the hold (Availability), reverses any transaction (Transactions), and reverses any redeemed promo code (Promotions).

None of these can be wrapped in a single ACID database transaction - they're different `DbContext`s, potentially different connections. The options are a distributed transaction coordinator (2PC), a formal outbox/reconciliation pattern, or sequential writes with hand-written compensation.

This decision was originally "compensating actions only" (see the git history of this file for that version). A later review of `CancelBookingHandler` and `MarkTransactionSucceededHandler` found two concrete instances of the risk window this document already called an accepted risk actually firing in a way hand-written compensation alone couldn't recover from:

- **`CancelBookingHandler`**: on a failed `ReleaseHoldAsync`, the caller's retry hit the `BookingStatus == Cancelled` early-return branch and never re-attempted the compensations. `ReconcileOrphanedBookedHoldsJob` (below) only treated a booked hold as orphaned when *no* booking row existed - a cancelled booking still has one, so its stuck hold was invisible to the job forever.
- **`MarkTransactionSucceededHandler`**: `MarkSucceeded()` committed in the Transactions context, then `ConfirmPaymentAsync` ran in the Bookings context. A crash between the two left `Succeeded` + booking still `Pending`; the retry path was closed (409 "already finalized"), and no sweep job covered this state.
- **`ConfirmBookingHandler`'s redemption step**: `IPromotionRedemption.RedeemAsync` commits atomically in the Promotions context (redemption cap incremented, the row inserted) before Bookings does anything with the result. A crash between that commit and the `Booking` insert (or the compensating enqueue in `ConfirmBookingHandler`'s own catch block) left the redemption permanently consumed against a booking that never existed - the same shape as `ReconcileOrphanedBookedHoldsJob`'s original "no booking row exists" case, but for redemptions, and with no equivalent job.

That's exactly the trigger this document already named for revisiting the outbox alternative ("either because compensation failures are observed happening in practice, or because the number of cross-module workflows grows enough that hand-writing a compensating action per workflow stops scaling"). The decision below reflects the result: compensating actions are still how the *forward* half of each workflow works, but the *follow-up* half - the step that runs after a module's own write is already durable, whether that's a genuine compensation on failure or the ordinary next step on success - now goes through a transactional outbox instead of a direct call.

## Decision

**Two different shapes, chosen per step, not per workflow.**

A cross-module step either (a) returns data the current write needs synchronously to proceed - `ConfirmHoldAsync`'s price/date snapshot, `RegisterHostAsync`'s `HostId` - or (b) runs after a local write is already durable and complete on its own, needing nothing back from the cross-module call to be correct. (a) stays a direct synchronous call with hand-written compensation on failure, exactly as before. (b) goes through the outbox described below.

**(a) Compensating actions, for calls the current write depends on:**

- Order writes so the **more authoritative fact goes first**. `MarkTransactionSucceededHandler` marks the transaction `Succeeded` before enqueueing the booking-side follow-up - "the payment succeeded" is true and stays true regardless of what happens next.
- `ConfirmBookingHandler`'s `ConfirmHoldAsync`/`RedeemAsync` calls stay direct and synchronous (their return values feed the `Booking` being constructed); `BecomeHostHandler`'s `RegisterHostAsync` call stays direct and synchronous (its `HostId` return value is what the response needs). If either fails, or a later step in the same handler fails after they succeeded, the compensation for *that* call - releasing the hold, reversing a redemption, deleting the host - is what moves to the outbox (see (b)).
- These compensations are idempotent and safe to no-op (`ReleaseHoldAsync` only acts on a hold that's still `booked`; `DeleteAsync` only acts on a `Host` that still exists) - retrying or racing them is never itself a source of corruption.

**(b) Transactional outbox, for follow-ups a durable local write doesn't need anything back from:**

- One shared `OutboxMessage` row type (`src/Infrastructure/Outbox`, its own project - see below), one dispatcher + one `[TickerFunction]` relay job per module that owns outbox messages (`Bookings`, `Transactions`, `Identity`), dispatched **inline immediately after the commit that wrote it**, with the relay job as a backstop for whatever the inline attempt didn't finish. This keeps happy-path latency identical to a direct call - the relay's poll interval only bounds the *failure*-recovery window, never the common case.
- The outbox row is written in the *same* `SaveChangesAsync()` call as the domain state change it accompanies (`booking.Cancel()`, `transaction.MarkSucceeded()`). A crash before that save loses nothing new; a crash after leaves both the state change and the durable intent to follow up together, never one without the other. In `ConfirmBookingHandler`'s and `BecomeHostHandler`'s compensation branches, the primary write already failed, so the message is written alone in its own `SaveChangesAsync()` call - `ChangeTracker.Clear()` runs first in every one of those branches, since the entities from the failed attempt are still tracked `Added`/`Modified` and would otherwise be re-attempted (and likely re-fail) by that save.
- Idempotency requirements carry over from (a) unchanged. `ReleaseHoldAsync`, `ReverseRedemptionAsync`, and `DeleteAsync` are documented safe to no-op on retry. `ReverseTransactionAsync` is "best-effort, never throws" by its own contract. `Transaction.MarkRefundPending`, reached from `TransactionsOutboxDispatcher` once `ConfirmPaymentAsync` returns false, is *not* naturally idempotent (a one-shot ledger transition, like `MarkSucceeded`/`MarkFailed`) - the dispatcher guards it explicitly (`if (transaction.TransactionStatus == Succeeded)`) so a retried dispatch of the same message is a safe no-op rather than hitting `TransactionAlreadyFinalizedException` and being mistaken for a real failure.
- `OutboxDispatcherBase` caps the *fast* retry loop at 10 attempts with capped exponential backoff (30s, 1m, 5m, 15m, 1h), then sets `DeadLetteredAt` rather than continuing to retry every poll interval. On dead-letter: an `Error` log, an OTel counter (`Outbox.OutboxTelemetry.DeadLettered`, mirroring `BuildingBlocks.Observability.CommandTelemetry`'s shape) tagged by module + message type, and a no-op-by-default `OnDeadLetteredAsync` hook a module can override for a specific message type that warrants more than logging/counting - all three fire once per row that *newly* crosses into dead-letter state, not once per subsequent retry. `Attempts` is never reset once a row dead-letters (see below), so without that distinction a permanently-broken message would re-trip the counter/log/hook every single hourly sweep forever, making the counter a rate of ongoing retries rather than a count of distinct failures - exactly the thing an alert threshold on it needs not to be. The counter and log are also deferred until *after* `CreateExecutionStrategy().ExecuteAsync` actually commits, not left inside the retried delegate - both are process-local side effects, not part of the DB transaction, so a transient deadlock/serialization failure that Npgsql's own retry-on-failure catches and retries would otherwise fire them again for what's really one logical attempt. `OnDeadLetteredAsync` stays inside deliberately: its own writes need to commit atomically with the rest of the row's outcome, and (like `TryHandleAsync`) it's already required to be idempotent, so re-running it across a transactional retry is safe by the same reasoning as everything else in that delegate.
- **Dead-lettered is not abandoned.** Each module's `OutboxRelayJob` also runs an hourly `SweepDeadLetteredAsync` - standard dead-letter-queue practice (Kafka/RabbitMQ/SQS shops all replay their DLQs), applied here by clearing `DeadLetteredAt` and giving the row one more `TryDispatchAsync` using its own already-recorded `Payload`. This was chosen over a bespoke reconciliation job that re-derives the right outcome from current state (e.g. re-computing what `CancelBookingHandler`'s refund amount should have been) - replaying the original payload is strictly safer, since the correct value was already computed once and durably stored. A renewed failure re-dead-letters immediately (`Attempts` is still >= the cap, so the row never actually leaves dead-letter state from an outside observer's perspective) but does not re-count; a renewed success clears normally. This is what actually closes the money-touching gap described below, not just documents it as accepted.
- **Its own project, not `SeedWork`/`Persistence`.** `OutboxMessage` is a persistence/delivery mechanism, not a domain concept - unlike `Entity`/`Money` in `SeedWork`, it's never touched by business logic, and splitting it across `SeedWork` (entity) + `Persistence` (config) would scatter one cohesive piece of infrastructure across two projects that own unrelated things. It's referenced the same way by three module projects at once, the same shape `Infrastructure/Jobs` already established for cross-cutting infra that isn't domain logic - so `src/Infrastructure/Outbox` is a new project, referenced directly by module `.csproj` files the same way they already reference `Persistence.csproj`. Zero dependency on any module, so no boundary-direction risk (ADR-0004).
- **Table names are module-prefixed** (`bookings_outbox_messages`, `transactions_outbox_messages`, `identity_outbox_messages`), not a bare `outbox_messages` - every module already shares one physical Postgres schema (see ADR-0004), so three modules mapping the same shared `OutboxMessage` CLR type to an identically-named table collided at migration time before this was caught.
- **No reflection anywhere in the dispatch path**, matching the reasoning ADR-0001/ADR-0002 already established: `OutboxDispatcherBase<TDbContext>.TryHandleAsync` is a plain virtual method each module overrides with a hand-written `switch` over `OutboxMessage.Type`, and payload (de)serialization always goes through the caller's own source-generated `<Module>JsonSerializerContext` - no dynamic type resolution, no `Activator.CreateInstance`.
- Background sweep jobs ([ADR-0002](0002-tickerq-for-background-jobs.md)) remain a last-resort backstop independent of the outbox, for the one class of leftover state neither mechanism fully closes on its own - see Consequences.

## Alternatives considered

- **Distributed transaction (`TransactionScope`/2PC) across the DbContexts.** Rejected as disproportionate: it adds real infrastructure complexity (a DTC or equivalent, cross-database transaction coordination) for a project at this scale, and Postgres's own cross-database distributed transaction story is not something to lean on casually.
- **Sharing an EF Core transaction across module `DbContext`s**, since all modules already share one physical Postgres instance. Would give true atomicity with zero eventual-consistency window, cheaper than an outbox. Rejected: it would quietly defeat the point of [ADR-0004](0004-module-boundaries-via-contracts-projects.md)'s module boundaries, which exist specifically to keep modules extractable into separate services/databases later - a shared-transaction write path only works as long as they stay co-located. An outbox stays correct independent of whether modules ever get physically separated.
- **A generic messaging library (`MassTransit`, `CAP`, `Brighter`).** Rejected: all three are messaging-framework-first, assuming a real broker and leaning on reflection-based handler/type resolution - the same category of thing ADR-0001 already rejected Hangfire for. This system only needs reliable in-process delivery between modules sharing one Postgres instance; none of that infrastructure is needed here.
- **`ZeroAlloc.Outbox`.** Architecturally the right shape - source-generated (`[OutboxMessage]` -> Roslyn-emitted writer/dispatcher), explicitly AOT-safe, no reflection, and it ships retry/backoff/dead-letter/a dashboard out of the box. Rejected anyway: at the time of this decision it had 6.5K total downloads, had been published within the last month, and was already at v2.5.2 - real maturity risk on top of what TickerQ already accepted, with less usage evidence behind it. It also pulls in a parallel `ZeroAlloc.*` ecosystem (`.Mediator`, `.Resilience`, `.Serialisation`, `.StateMachine`, `.ValueObjects`) including its own `ZeroAlloc.Mediator`, which collides conceptually with the `Mediator.SourceGenerator` this codebase already uses everywhere. For something this small (~3-4 files per module), hand-rolling it avoids both problems. If a library in this space develops a real track record, it's worth revisiting - the case against it here is maturity and dependency footprint, not the pattern.
- **Outboxing the forward calls (`ConfirmHoldAsync`, `RegisterHostAsync`) too, for full uniformity.** Rejected: those calls return data the local write needs synchronously, so deferring them to a relay would mean restructuring the response flow (e.g. pre-generating a `HostId` client-side and creating the `Host` row asynchronously) - a materially bigger change than the actual trigger (two compensation-loss bugs) called for.

## Consequences

- **A real, accepted risk window remains, though it's bounded, visible, and self-healing rather than open-ended and silent.** A dead-lettered outbox row never leaves any entity in a contradictory state - each side's own write already committed and stays individually valid. What's missing is the follow-up, and every message type now gets a real second chance at it, via one of two independent mechanisms:
  - **`ReleaseHoldOutboxMessage` and `ReverseRedemptionOutboxMessage` each get a purpose-built backstop**, not just the generic sweep - both for the same underlying reason: the forward call each compensates for (`ConfirmHoldAsync`, `RedeemAsync`) commits durably to its own module's database *before* Bookings ever gets a chance to create the `Booking` or enqueue anything, so a process crash in that window leaves nothing in the outbox to retry at all, not even a row to dead-letter. **(Superseded by ADR-0017:** the diagnosis is right, but both jobs below reconstruct by cross-module query a fact nobody recorded. ADR-0017 records it instead - a `PendingBookingIntent` written before the first cross-module call - and replaces both jobs, plus `IHoldLookup`/`IRedemptionLookup`, with one job driven off that row. Both jobs described below are now deleted.**)**
    - `Bookings.Jobs.ReconcileOrphanedBookedHoldsJob` asks Availability (via `IHoldLookup.GetBookedHoldIdsOlderThanAsync`) for `'booked'` holds older than a grace period, checks which have no matching `bookings.hold_id` row *or* whose booking is `Cancelled`, and releases the orphans through `IHoldConfirmation.ReleaseHoldAsync`. Originally scoped only to "no booking row exists" (a `ConfirmBookingHandler` crash between `ConfirmHoldAsync` and the `Booking` insert); widened to also cover a `Cancelled` booking once `CancelBookingHandler`'s own hold release started going through the outbox.
    - `Bookings.Jobs.ReconcileOrphanedPromotionRedemptionsJob` is the same shape for `RedeemAsync`: `IPromotionRedemption.RedeemAsync` atomically increments a `Promotion`'s redemption cap and inserts the `PromotionRedemption` row in one Dapper transaction, entirely independent of anything Bookings does afterward. A crash between that commit and the `Booking` insert (or the compensating enqueue in `ConfirmBookingHandler`'s own catch block) leaves the redemption permanently consumed - cap decremented, guest email marked used - against a booking that was never created, with nothing to retry since no outbox row was ever written. Asks Promotions (via the new `Promotions.Contracts.IRedemptionLookup.GetActiveRedemptionBookingIdsOlderThanAsync`) for still-active (`ReversedAt IS NULL`) redemptions older than a grace period, checks the same "no booking row *or* `Cancelled`" condition against `bookings`, and reverses the orphans through the existing `IPromotionRedemption.ReverseRedemptionAsync` - both jobs are functionally the same query shape, applied to a different table.
  - **`ReverseTransactionOutboxMessage`, `ConfirmBookingPaymentOutboxMessage`, and `DeleteHostOutboxMessage`** rely on the generic hourly `SweepDeadLetteredAsync` described above - no bespoke reconciliation job needed, since replaying the row's own original `Payload` is already the correct fix, not an approximation of one. These three don't have the same "commits before Bookings gets a chance" exposure `RedeemAsync`/`ConfirmHoldAsync` do - their forward calls (`ConfirmPaymentAsync`, `ReverseTransactionAsync`, `DeleteAsync`) are already outbox messages themselves (or a compensation branch reached after a local write), so a crash before dispatch just means the outbox row's own `SaveChangesAsync` never committed either, and nothing was durably promised in the first place.
  - What's still genuinely open: a message whose underlying failure is *not* transient (a real bug, not a temporary outage) retries hourly forever without succeeding. That's a correct outcome, not a gap - each attempt is visible (log + counter), and the fix is deploying the actual bug fix, after which the very next sweep succeeds with no manual "replay this message" step required. A permanently-broken message still needs a human to notice the recurring `Error` log/counter and investigate, same as any other persistent failure.
- **The reconciliation job's own window is a second, smaller accepted risk window, not a closed one.** *(Closed by ADR-0017 - an intent row does not age out of reach, so this window and its "unreachable forever" tradeoff no longer exist.)* `ReconcileOrphanedBookedHoldsJob` only looks at `'booked'` holds within a bounded lookback (a 2-day `ReconciliationWindow`, capped at 1000 candidates per run) to avoid scanning this app's entire booking history every 5 minutes. An orphan older than that window - or one that arrives in a run that hits the 1000 cap while older orphans are still queued behind it - is invisible to the job forever, not just delayed; it logs a warning when it hits the cap, but recovering a hold past the window itself is a manual query, not something any job will do for you.
- **`Bookings` and `Transactions` were already mutually dependent before this pass** (ADR-0004's Consequences) - `BookingsOutboxDispatcher`'s use of `Transactions.Contracts.ITransactionReversal` is the same pre-existing edge, not a new one.
- **`CancelBookingHandler`'s response is decided before the inline dispatch, not read back after it.** It reports `RefundPending: true` with the computed figure whenever a `Succeeded` transaction existed at the moment of cancellation, regardless of whether that request's own dispatch attempt then landed. This is deliberate: reading `GetRefundSnapshotAsync`/`GetSucceededTransactionAmountAsync` *after* dispatching made the response a function of whether the attempt won the race - a landed reversal moves the transaction past `Succeeded`, so the snapshot appears and the Succeeded lookup empties at the same instant - and the identical request answered `RefundPending: false` with a settled figure or `true` with a computed one depending on timing the caller cannot see or control. The inline dispatch is a latency optimisation; the durable outbox row is the guarantee, so only the latter belongs in the contract. An idempotent re-cancel still reports what actually landed, because by then it is reading state that settled in an earlier request rather than its own writes.
- Every new cross-module write path should be evaluated against this same checklist: does the current write need data back from the call (stays a direct compensating call), or does it run after a local write that's already durable and complete on its own (goes through the outbox)? Authoritative-write-first ordering and idempotency apply either way.
