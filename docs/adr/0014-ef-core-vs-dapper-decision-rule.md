# 0014 - EF Core vs. Dapper: which owns a given database operation

**Status:** Accepted

## Context

This codebase already mixes EF Core and Dapper - it has since `HoldAvailabilityHandler` and `GetPriceCalendarHandler` were first written - but the split was never written down as a rule. Each usage was justified locally, in its own doc comment: `UnitAvailabilityHold`'s "business logic never loads it through EF change tracking... HoldAvailabilityHandler writes to it with hand-written Dapper SQL... instead of DbContext.SaveChanges() - see docs/adr/0010", `PromotionRedemption`'s "written through Dapper inside the same transaction as Promotion's redemption-count increment, not DbContext.SaveChanges()", `PricingRule`'s "CRUD goes through EF change tracking normally... RedemptionCount's own hot-path increment is the one exception, done via raw SQL." Each of these is correct in isolation. None of them, read alone, tells a future contributor adding a new hot-path table which tool to reach for.

That's a real risk, not a style nitpick: without a stated rule, the natural failure modes are (a) reaching for Dapper out of habit on a path that's genuinely just CRUD, adding parsing/mapping complexity for nothing, or (b) reaching for EF on a path that actually needs a Postgres-specific SQL shape EF can't translate, and hitting exactly the problems (`generate_series`, guarded `UPDATE ... RETURNING` in one round trip, catching a specific constraint-violation error code) the existing Dapper usages already exist to solve.

## Decision

Three tiers, in order of preference - drop to the next tier only when the one above genuinely can't do the job:

**Tier 1 - EF Core LINQ + change tracking (`SaveChangesAsync`).** The default. Used for the large majority of the app: standard CRUD on an aggregate root, and any read expressible as ordinary LINQ. Covers `Property`, `Unit`, `Booking`, `Transaction`, `ApplicationUser`/`RefreshToken` (issuance), `StayReview`/`GuestReview`, `PricingRule`, `Promotion` (everything except its redemption counter), `BookingManagementToken`. Concurrency safety on this tier still comes from a real database constraint, not an application-level check-then-act - `InitiateTransactionHandler`'s `AnyAsync` pre-check is a friendly-error fast path only; the partial unique index is the actual authority, enforced by catching `DbUpdateException` wrapping a `PostgresException { SqlState: UniqueViolation }`. Reaching for Dapper is not a prerequisite for handling concurrency correctly - EF can enforce a DB constraint's authority just as well as Dapper can, by catching the same error at its own layer.

**Tier 2 - EF Core's `ExecuteUpdateAsync`/`ExecuteDeleteAsync`.** A bulk, untracked, single-statement operation that LINQ can express, used when change tracking would be pure overhead (a pure delete/update with nothing to materialize) or when a conditional single-statement mutation needs atomicity a load-then-save round trip can't give it. `AuthTokenProvider.ValidateRefreshToken`'s conditional consume (`UPDATE ... WHERE !IsRevoked`, race-safe by construction - two concurrent callers can't both match the same row) and `RevokeFamilyAsync` are both this tier for atomicity; `ExpiredRefreshTokensSweepJob`'s nightly cleanup is this tier purely because there's nothing to load and mutate, just rows to delete.

**Tier 3 - Dapper, raw SQL against `dbContext.Database.GetDbConnection()`.** Reserved for what LINQ genuinely cannot express, or a Postgres-native construct EF has no translation for:

- `generate_series(...)` cross-joined against a table (`GetPriceCalendarHandler`) - no LINQ shape produces this.
- A single atomic `UPDATE ... WHERE <guard> RETURNING <several columns>`, needing the guard and the returned row in one round trip (`HoldConfirmation.ConfirmHoldAsync`) - EF's `ExecuteUpdateAsync` has no `RETURNING` equivalent in the general LINQ API.
- Catching a specific Postgres error code as the actual concurrency guarantee where the constraint itself has no EF fluent representation at all - the GIST exclusion constraint HoldAvailabilityHandler's insert relies on (see [ADR-0010](0010-postgres-exclusion-constraint-for-double-booking.md)); contrast with Transactions' partial *unique* index above, which does have a fluent equivalent (`HasFilter`) and stays Tier 1 for exactly that reason.
- A genuinely hot, high-concurrency write path where the entity has no business methods and is never meant to be loaded/tracked at all (`UnitAvailabilityHold` - see its own doc comment). All of its writes are pinned to Dapper as a deliberate, absolute, zero-exception rule for this one table specifically, even where `ExecuteUpdateAsync`/`ExecuteDeleteAsync` (Tier 2) could technically achieve the same "never tracked" property - see the audit note below for why that line was drawn on purpose.

When raw SQL is genuinely needed, it goes through Dapper on the DbContext's own connection - never EF's own `FromSqlRaw`/`ExecuteSqlRaw`. One raw-SQL mechanism in the codebase, not two with different parameterization and mapping conventions to remember.

**The split is per-operation, not per-table or per-class.** `PromotionRedemption.RedeemAsync` reads validation data (the promotion, the unit, the property) via ordinary Tier 1 LINQ, and only drops to Tier 3 for the one atomic increment-and-insert pair that needs a shared transaction and a guarded `UPDATE`. `GetPropertiesHandler` reads `UnitAvailabilityHolds` - a table whose *writes* are Tier-3-only - via a plain Tier 1 `.Any(...)` correlated-EXISTS translation, because that specific read has no Postgres-specific shape to it; it's the write paths on that table that do. A `DbSet<T>` existing on a module's `DbContext` is evidence the module owns that table's *schema*, not evidence of which tier its runtime operations use - check the entity's own doc comment (an established habit in this codebase) before assuming either way.

## Alternatives considered

- **EF everywhere, no Dapper.** Rejected: [ADR-0010](0010-postgres-exclusion-constraint-for-double-booking.md) already established Npgsql's EF provider has no fluent API for the exclusion-constraint semantics `HoldAvailabilityHandler` depends on, and `generate_series` has no LINQ translation at all. Forcing these into EF would mean hand-rolling something worse than Dapper to get the same SQL out.
- **Dapper everywhere, EF only for migrations.** Rejected: would discard change tracking, LINQ readability, and the migration-diffing workflow for the ~90% of operations that are plain CRUD with no hot-path or Postgres-specific need - pure complexity tax, no corresponding benefit.
- **A strict per-table assignment ("this table is Dapper's, that one is EF's").** Rejected once traced through the actual code - `PromotionRedemption` and `GetPropertiesHandler` already prove the right granularity is per-operation. A strict per-table rule would have forced `GetPropertiesHandler`'s simple availability check into hand-written SQL for no reason, or forced `PromotionRedemption`'s validation reads into Dapper alongside its one genuinely atomic write.

## Consequences

- New hot-path or Postgres-feature-shaped code should default to Tier 1, reach for Tier 2 only for a conditional-atomic single-statement mutation or a pure bulk delete/update, and drop to Tier 3 only once Tier 1/2 are confirmed unable to express what's needed - checked against the provider's actual LINQ/fluent capability first, the same discipline [ADR-0011](0011-prefer-model-config-over-migration-sql.md) already established for raw migration SQL.
- **Audit performed against the codebase as of this ADR** (all `Dapper`-referencing files under `src/`, plus a check for any `FromSqlRaw`/`ExecuteSqlRaw`/`ExecuteSqlInterpolated` usage): no EF raw-SQL escape hatches exist anywhere, and every Tier 3 usage maps to one of the four justifications above. One asymmetry was found and deliberately left as-is rather than "fixed": `ExpiredHoldsSweepJob` (Catalog) sweeps `unit_availability_holds` via a hand-written Dapper `DELETE`, while the structurally identical `ExpiredRefreshTokensSweepJob` (Identity) does the same job via `ExecuteDeleteAsync` (Tier 2). Both are provably correct; the Catalog job stays Dapper on purpose, so that "every write to `unit_availability_holds` is Dapper, no exceptions" remains a single sentence anyone can audit for the one table in this app where getting that wrong is a real double-booking risk, rather than "every write is Dapper except this one bulk delete, which is fine because it doesn't track anything either." The Identity table carries no comparable single-invariant risk, so its sweep job stays on the simpler, more idiomatic Tier 2.
- `Bookings` and `Hosts` both carry a `[module: DapperAot]` assembly attribute (`DapperAotConfiguration.cs`) despite neither module issuing any Dapper queries today. Harmless (the attribute has no effect without a query to source-generate against) and left in place rather than removed - likely present for parity with modules that do use Dapper, and costs nothing to keep if either module ever needs Tier 3 later.
- **A missing rule, found the hard way.** The audit above confirmed every Tier 3 site maps to one of the four justifications, but never checked whether each one correctly restates the global soft-delete filter (`ApplySoftDeleteQueryFilter`) that Tier 1 gets for free. It doesn't apply automatically to raw SQL - `GetPriceCalendarHandler`'s `CROSS JOIN units u WHERE u.id = @UnitId` had no status predicate at all, so an archived unit's calendar was still returned and priced. Fixed by adding `AND u.status <> 2` (confirmed empirically against a real Postgres instance that `EntityStatus` is stored as its raw integer ordinal, not a string like `Currency` - the first attempt used `'Archived'` and failed with `22P02: invalid input syntax for type integer`). **The rule going forward:** any Tier 3 query joining an `Entity`-derived (soft-delete-governed) table must restate `status <> 2` by hand; this is not optional and was not previously written down anywhere.
- **A deliberate, documented exception to that same rule.** `Bookings.Jobs.ReconcileOrphanedBookedHoldsJob`'s `NOT EXISTS (SELECT 1 FROM bookings b WHERE b.hold_id = h.id)` check does *not* restate the soft-delete predicate on `bookings`, on purpose - an archived (soft-deleted) booking still happened and should still protect its hold from being released out from under it. The soft-delete filter governs visibility to ordinary queries, not whether the booking exists; applying it here would be exactly the kind of "fix" the rule above should never trigger, and the job's own code comment says so explicitly so a future reader doesn't reflexively add it.
